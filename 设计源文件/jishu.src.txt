# 《汴河两岸》技术方案：掌厨镜与试味回路

!sub 两项可延伸到现实厨房的手机技术 · 食材分配 × 试味回路 · 八周原型
!date 2026-09-26 · 据《技术(1).pdf》整理；验货的操作人改为玩家（3 级小二可开自动验货）

!box 本项目计划在游戏中验证两项由手机完成的交互技术："掌厨镜"根据验货结果把可用食材分配给当前订单；"试味回路"把小份试吃反馈、剩余食物、顾客评价和每月点单变化结合起来，帮助小二决定下一版做法和备货量。两项技术既服务于游戏角色，也能形成供小型餐饮场景试用的独立原型。游戏里的验货和试味规则见第二部分 03、06 节。

## 01 掌厨镜：验货后重新分配食材

%cols 16 84
| 步骤 | 做法 |
| 拍摄与清点 | 玩家用手机拍一盘指定食材；程序标出每件的位置和数量，使用者可以手动改正 |
| 人工验货 | 玩家点选不可使用的个体并丢弃。手机只记录结果，不凭照片宣称食材安全 |
| 订单分配 | 程序依据可用数量、大小等级、菜品需求和先后顺序，把食材分给各张订单 |
| 即时反馈 | 显示还能完成几单、哪单缺料、剩余多少；小二据此调整推荐和采购 |

- 游戏中的位置：便宜批次可能有更多坏料；玩家验货后，可用份数立刻变化，小二升到 3 级后也可以开自动验货。小二通过掌厨镜安排剩下的食材（游戏里小二 2 级学会砍价后才独立采购），玩家厨师接到调整后的订单再动手做菜。哪道菜的可做份数不够，小二就不再向新客推荐；小二升级后推荐更准（2 级约七成、3 级约九成，见第二部分 05）。
- 现实中的用途：小饭馆遇到到货品质不一或临时缺货时，只拿手机就能快速清点，并确认哪些订单仍能按要求完成。原型先限定一种容易逐件清点的食材；算法负责"把可用个体分给订单"，不负责生成菜谱。

## 02 试味回路：让新菜从试吃走向备货

- 小二向少量顾客提供新菜的小份试味。顾客在手机上回答"愿不愿再点""哪个味道过强或过弱""这个价格能否接受"。下一轮试味由程序比较两种已定义的做法，再建议小二向哪类顾客推哪一种；玩家厨师仍亲手完成烹饪。
- 这项技术在完整游戏里特别适合时空门带来现代食材的情节：宋代顾客的陌生、接受或拒绝不再是预写的固定台词，而会依据试玩版采集的试味和点单数据改变；这是以后的方向，现行版本先用第二部分 03 的固定概率。现实原型可以供餐馆测试新菜或限时菜单。

### 把试味、剩余和月度变化连起来

试味只回答"第一口感觉如何"；要不要增加备货，还要看真正卖出的数量和吃完后的结果。

%cols 18 82
| 数据 | 记录什么 |
| 每月点单人数 | 按菜品和版本统计实际下单人数，算出和上月相比的增减 |
| 食客评价 | 评分和结构化的味觉反馈，例如"太酸""刚好""愿意再点" |
| 餐后剩菜 | 按份量粗略记录客人端回的剩余；它提示口味或份量问题，不能单独等同于"不喜欢" |
| 厨房剩余 | 当日没卖出的成品或已备原料；它更直接反映备货过量 |

- 系统怎样给建议：先根据最近几个月的实际点单人数形成一个基础需求范围，再把两种剩余分别当作"顾客食用情况"和"后厨备货情况"检查，同时对照评价和版本差异。输出的是"下一轮试味哪一版、建议先备多少份、为什么"，并显示不确定性；小二决定是否采纳。
- 例子：某道新菜的点单人数连续增长，但顾客退回的剩菜也多、评价常提"太酸"。系统建议继续试低酸版本，暂时只小批量备货；如果低酸版本评价改善、剩菜减少，再考虑扩大供应。如果厨房总有成品卖不完，即使评分不错，也不直接按点单增长的比例增加备货。

## 03 两项技术怎样接在一起

- 试味回路给出下一营业日的预计份数；掌厨镜在食材真正到货、坏料被丢弃后重新计算可完成的订单。前者管"计划多少"，后者管"今天实际能做多少"。小二负责采购（2 级学会砍价后才独立去买）、做法和推荐，玩家负责验货和烹调；小二升到 3 级后可以接手验货。
- 游戏里暂时只做小份试味和"欢迎"加成（第二部分 03）；给小二的备货建议先只在手机原型里验证，以后可以放进采购页。
- 手机交互用一个网页原型就能演示：员工端负责拍摄、点选坏料、确认剩余量；顾客端通过二维码打开几道试味问题。不需要另配相机或专用称重设备，但第一版的份量记录需要人工确认。

## 04 技术实现与八周验证

核心算法由项目自己设计；外部 API 只用于可选的自然语言解释，不替代库存、分配和估算计算。

%cols 16 84
| 时间 | 原型实现路径 |
| 第 1—2 周 | 完成手机页面、订单和食材数据结构；确定一种食材、两道使用它的菜 |
| 第 3—4 周 | 完成拍摄清点、人工剔除、可用份数与订单分配；接入游戏的验货和小二决策 |
| 第 5—6 周 | 完成两种新菜做法的试味页，输入评价、餐后剩菜、厨房剩余和按月点单数据，生成解释性建议 |
| 第 7—8 周 | 完成双模块联动、游戏演示和手机现实场景演示；修正界面和计算错误 |

- 验收方式：用同一批食材演示"丢弃两件前后，可完成订单数怎样变化"；用两种做法和若干顾客试味结果，演示建议版本怎样改变；再输入多个月的点单、评价和两类剩余量，看建议备货量和解释是否随数据合理变化。
- 数据界限：八周内攒不出足够的真实月度历史。课堂演示可以用明确标为"模拟"的连续数月样本验证流程；以后经过真实餐饮试用，才能检验月度估算的误差和是否真的减少浪费。照片也不能独立判定食品安全，丢弃与否由人确认。

## 05 设计新意与现有技术

- 现有系统已经分别提供厨房食物浪费记录、餐桌即时评价或常规统计预测。本提案把新菜小份试味、餐后剩菜、厨房剩余和月度点单变化连到下一次小批量试验，并把这个备货建议接到"验货后立即重排订单"的手机流程。
- 这里主张的是具体的交互和组合方法；还不能声称全世界没有相似产品，也不能声称有专利新颖性[1][2]。
